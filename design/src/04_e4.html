4. Arquitectura y modelo de datos

La app sigue el patrón MVVM con un flujo unidireccional de datos: la interfaz observa un estado inmutable, el ViewModel lo produce y el repositorio decide de dónde sale. La misma arquitectura se conecta con una API REST y con un modelo de datos de solo lectura representado por data classes de Kotlin.

4.1 Arquitectura MVVM y responsabilidades

Flujo unidireccional

El usuario toca un botón → la UI emite un evento → el ViewModel actualiza su estado o llama al repositorio → el repositorio consulta la API → el ViewModel recibe el resultado y publica un nuevo UiState → Compose recompone solo lo que cambió. Este ciclo se repite en todas las pantallas y explica por qué la app puede mostrar estados de carga, error y éxito sin lógica duplicada. 

// Ejemplo real de la capa de presentación
class HomeViewModel(
    private val repository: PatientRepository = ServiceLocator.patientRepository,
) : ViewModel() {
    private val _state = MutableStateFlow(HomeUiState())
    val state: StateFlow<HomeUiState> = _state.asStateFlow()

    fun load() = viewModelScope.launch {
        _state.update { it.copy(isLoading = true, error = null) }
        runCatching { repository.nextAppointment() }
            .onSuccess { appointment ->
                _state.update { it.copy(isLoading = false, nextAppointment = appointment) }
            }
            .onFailure { error ->
                _state.update { it.copy(isLoading = false, error = error.message) }
            }
    }
}

4.2 Arquitectura de datos y stack tecnológico

La arquitectura de datos muestra con qué software está hecho el sistema y por dónde viajan los datos. Se organiza en cuatro zonas —clientes, borde, servidor y datos— más una banda de seguridad transversal. Los logos son de Simple Icons (CC0) y de sus respectivas marcas.

ZonaQué contieneProtocolo / frontera
ClientesApp Android (Kotlin, Compose, M3, Retrofit, ZXing, OSMDroid, Biometric) y portal web (HTML + Jinja2).HTTPS · REST/JSON · cookies HttpOnly en el portal.
BordeCloudflare (DNS/TLS), Nginx Proxy Manager y Let's Encrypt.TLS 1.2/1.3, HSTS, proxy inverso y límites de tamaño.
ServidorUbuntu VPS, Docker Compose, FastAPI/Uvicorn, Pydantic, SQLAlchemy/Alembic, Jinja2, ReportLab, PyJWT, Argon2, PyOTP.API REST, validación, generación de PDF y correo.
DatosPostgreSQL (13 tablas, 3FN), volumen Docker para PDFs, Resend para correo y OpenStreetMap para tiles.SQL asyncpg por red interna; archivos con SHA-256 + HMAC.
Por qué esta arquitectura. La app no guarda datos clínicos: los pide a la API en cada consulta. Eso reduce el riesgo si el teléfono se pierde y garantiza que el paciente vea siempre la misma información que el hospital. PostgreSQL nunca publica puertos; el único punto expuesto es el proxy HTTPS.

4.3 Flujo de datos del check-in

El check-in es el mejor ejemplo de la arquitectura porque cruza las cuatro capas: cámara (UI), ViewModel, repositorio, Retrofit, API, PostgreSQL y portal. La operación es idempotente: si el paciente repite la llamada, la llegada no se duplica. Además, la app nunca escribe datos clínicos; solo confirma la llegada.

PasoResponsableQué ocurreEvidencia / regla
1Recepción (portal)Abre la cita y muestra el QR con su código de respaldo.Cada cita genera un código único.
2App (UI)El paciente toca “Abrir cámara” y escanea el QR.ZXing en orientación vertical.
3App (ViewModel)Envía el código al repositorio y muestra estado de carga.No bloquea el hilo principal.
4API (FastAPI)Valida JWT, propiedad de la cita, código, estado y ventana.401/403/400/409 según el caso.
5PostgreSQLActualiza checked_in_at y registra la auditoría.Operación idempotente.
6API → AppResponde 200 con especialidad, consultorio y hora.La app muestra “Llegada confirmada”.
7PortalLa sala de espera refleja la llegada del paciente.El médico abre la consulta precargada.

4.4 Modelo de datos de la app

El modelo de la app es una proyección de solo lectura del modelo del backend. No todas las tablas se exponen: el paciente ve únicamente lo que necesita. Los identificadores (patientId, documentId) referencian entidades del servidor y permiten navegar sin duplicar datos.

RelaciónCardinalidadCómo se representa
PatientProfile → PatientAppointment1 a 0..*El perfil autenticado consulta sus citas; la cita no repite el perfil completo.
PatientProfile → PatientConsultation1 a 0..*Cada consulta conserva patientId y los datos del médico.
PatientProfile → PatientDocument1 a 0..*Documentos del expediente con sha256 y metadatos.
PatientProfile → PatientStudy1 a 0..*Estudios solicitados; documentId apunta al resultado cuando está listo.
PatientProfile → PatientPrescription1 a 0..*Recetas emitidas; documentId apunta al PDF firmado.
PatientPrescription → PatientPrescriptionItem1 a 1..*Lista de medicamentos con dosis, frecuencia y duración.
PatientStudy / PatientPrescription → PatientDocument0..1 a 0..1El documento es el PDF que el paciente descarga; el hash permite verificarlo.

4.5 Data classes de Kotlin

Las clases siguientes son las que existen en el proyecto (data/model/ClinicalModels.kt y data/model/AuthModels.kt). Se anotan con @Serializable y @SerialName para mapear el JSON del backend sin acoplar los nombres de Kotlin a los de la API.

¿Por qué data classes y no entidades?

La app no es un ORM: consume JSON. Las data classes son inmutables, serializables y fáciles de comparar; el mapeo con @SerialName desacopla los nombres del backend de los de Kotlin. Así el contrato se puede versionar sin romper la UI.

¿Por qué solo lectura?

El paciente no debe poder alterar un diagnóstico, una receta o un resultado. La app solo envía login, check-in y acciones de seguridad; todo lo clínico lo escribe el personal desde el portal y queda en la bitácora.
